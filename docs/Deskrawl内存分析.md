# Deskrawl 为什么吃这么多内存

> 结论先行：**Deskrawl 本身不"漏"内存，它是把峰值一次性吃下来之后不还。**
> 你能从外面改的，是"它最多能常驻多少"——这正是内存管家做的事。

本文的结论来自三处证据：游戏本体的文件结构、游戏自己的日志、以及对 Windows 内存 API 的实测。

---

## 一、先看清楚"内存"到底指什么

任务管理器里那一列叫**工作集（Working Set）**，意思是"此刻真的躺在物理内存里的页"。
另一个数字叫**提交（Commit）**，意思是"这个进程向系统预约了多少地址空间，不管是 RAM 还是页面文件"。

Deskrawl 的典型形态是：

| 指标 | 典型值 | 含义 |
|---|---|---|
| 工作集 | 2～6 GB | 任务管理器看到的，也是你觉得"卡"的直接原因 |
| 提交 | 往往比工作集大 30%～100% | 预约了但被系统换出的部分 |
| 私有提交 | 接近提交 | 其中真正属于它自己的（不含共享 DLL） |

**所以"占用高"= 工作集高**。把工作集按住，任务管理器立刻就下来了。

---

## 二、这 2～6 GB 花在哪了

用内存管家的「分析原因」能在你自己的机器上逐项列出，下面是它背后的结构：

### 1. 1.2 GB 的资源包被映射进进程（最大头）

```
Deskrawl_Data/sharedassets0.assets.resS    1.2 GB   ← 纹理/音频原始数据
Deskrawl_Data/sharedassets0.assets         415 MB   ← 资源索引与元数据
Deskrawl_Data/resources.assets.resS         69 MB
Deskrawl_Data/sharedassets0.resource        29 MB
Deskrawl_Data/level0                        25 MB
```

Unity 不是"把 1.2 GB 读进内存"，而是**内存映射**这个文件，用到哪页读哪页。
听起来很省，但读过的页会留在工作集里**不主动归还**——玩得越久、跑的地图越多，常驻就越接近 1.2 GB。

这类内存在体检报告里标记为「映射文件」，**不占提交**，但你一按"回收"就能把它挤出去（下次用到再从硬盘读）。

### 2. Unity 6 的 IL2CPP + Boehm GC：只涨不缩

- 引擎：Unity **6000.3.6f1**，脚本后端 **IL2CPP**（`GameAssembly.dll` 就有 64 MB 的机器码）。
- IL2CPP 用的垃圾回收器是 **Boehm GC**：保守式、**不压缩、不主动把空页还给系统**。
- 结果：开局加载场景冲到峰值，之后即使对象都释放了，堆的高水位还在。

这就是"玩一会儿不玩也占着 3 GB"的根因。**这个行为改不了**（除非改游戏），但可以从外面把它的常驻按下去。

### 3. mod 把一整个 .NET 运行时塞进了游戏进程

你装了 X1X 的 Doorstop 注入：

```
winhttp.dll              ← Doorstop 劫持，游戏一启动就被注入
doorstop_config.ini      target_assembly = X1X\X1X.DeskrawlHost.dll
                         coreclr_path    = dotnet\coreclr.dll
dotnet/  (21 MB)         ← 完整 CoreCLR 运行时
X1X/     (388 KB)        ← DeskrawlHost.dll + dobby.dll
```

也就是说 **Deskrawl.exe 这个进程里同时跑着 Unity 的 IL2CPP 和一套完整的 .NET 运行时**。
后者自带托管堆、JIT 编译的代码页、元数据——全部算在游戏的私有提交里。这部分通常 200～500 MB，
而且托管堆同样是"涨上去不下来"的性格。

### 4. 透明窗口 + 每帧重绘

游戏日志 `%LOCALAPPDATA%Low\First Day Games\Deskrawl\Game.log` 里刷屏的是：

```
[TransparentWindow] placed (x,y) 1536x864 ...
```

每一帧都在重新摆放一个透明窗口。透明窗口要走 DWM 合成，窗口越大、刷新越频繁，
合成缓冲和 GDI/USER 对象就越吃内存。日志里还有 420 条 `Material ... doesn't have _Stencil property` 警告——
说明它在反复创建材质变体，这些变体同样堆在内存里。

### 5. 助手是另一个进程，不背这个锅

「Deskrawl 装备助手 / X1X Helper」是独立的 `pythonw.exe` + 浏览器面板：
纯 Python 标准库写的本地 HTTP 服务，内存通常几十 MB。
**它不会让游戏变吃内存**，但在管家的进程列表里能看到，想一起管也可以。

## 三、为什么"越玩越涨"，以及为什么会卡

1. 进新地图 → 新纹理进映射 → 读过就留着 → 工作集涨。
2. 峰值过去 → Boehm GC 不还页 → 工作集不降。
3. 物理内存被占满 → Windows 开始换页 → 你的其他软件（浏览器、Discord）开始卡。
4. 页面文件涨到几十 GB（你这台机器的页面文件上限是 **56.9 GB**），系统从不拒绝它申请内存——
   直到 RAM 真的被榨干。

**所以问题的本质不是"泄漏"，是"缺少上限"。** 而这正好是你想要的：由你决定它能占多少。

---

## 四、这个工具怎么把它按住

Windows 给了三个层次的开关，管家把它们做成了三个按钮：

| 方式 | 调的 API | 效果 | 风险 |
|---|---|---|---|
| **工作集上限**（推荐） | `SetProcessWorkingSetSizeEx(..., QUOTA_LIMITS_HARDWS_MAX_ENABLE)` | 超过上限的页被换出，任务管理器数值被钉住，进程继续跑 | 读到被换出的页会卡一下 |
| **上限 + 定时回收** | 上面 + `EmptyWorkingSet` 每 20 秒 | 常驻更低，闲置页立刻清出 | 回收瞬间可能掉帧 |
| **提交硬上限** | 作业对象 `JOB_OBJECT_LIMIT_PROCESS_MEMORY` | 真正的天花板，超了系统直接终止进程 | 会闪退，慎用 |

另外还有 `SetProcessInformation(ProcessMemoryPriority, VERY_LOW)`：把它的页面排在回收队首，
配合上限使用更顺。

### 给 16 GB 机器的建议值

| 你的用法 | 建议上限 |
|---|---|
| 只开游戏，别的都不开 | 8～10 GB |
| 一边游戏一边浏览器/语音 | **4～6 GB** |
| 小地图、低画质、后台还要干活 | 3 GB |
| 硬核自律（超了就闪退） | 2～3 GB + 提交硬上限 |

上限不要低于 1.5 GB：Unity 光加载资源和着色器就要这么多，压太狠会疯狂读盘，反而更卡。

---

## 五、怎么自己验证

1. 启动游戏，打开内存管家，它会自动接管 `Deskrawl.exe`。
2. 点「分析原因」，等 1 秒，报告里会列出：映射文件多少、私有堆多少、哪个 DLL 最占地方。
3. 拖滑杆定上限 → 点「应用上限」。
4. 回游戏玩 10 分钟，回来看看曲线是否被红线压住。

报告可以点「保存报告」存成 txt，方便对比调参前后的差别。
